# Read Me - Delivery Roadmap and SRS Review

**Spec:** `srs.md` (SPEC-001, draft 2026-10-01)

The SRS covers six subsystems (text pipeline, native storage and intake, playback service, UI,
Obsidian bridge, release) and six spikes that it says must run before implementation. That is
too much for one plan, and several later designs depend on spike answers. So the work is split
into one plan per phase. Only Phase 0 is written in full now. Each later plan is written when
its gating spikes have answers, so it argues from measured facts, not guesses.

## SRS review (2026-10-01)

Findings from reviewing `srs.md` against the prototype (`note-reader-local/companion/android`),
the RN 0.87 template, and the reference device. F1-F10 are already resolved in the SRS, so
numbering continues at F11.

| # | Finding | Proposed resolution | Status |
|---|---|---|---|
| F11 | `library` (SQLite) is in TS, but intake, the Fetcher, and PlaybackService all have to write while JS may not be running (R-M02, R-M03, R-M07, R-M11: position after every sentence, archive on the last sentence, both with the screen off). | **Kotlin owns the database** (platform `android.database.sqlite`, no npm SQLite). JS reads and writes through `ReadMeSpeech`. The TS `library` module becomes a typed facade. | **Owner decided 2026-10-01**; ADR 0001 lands with the scaffold (Phase 0 Task 2) |
| F12 | No state between "fetched" and "extracted". Extraction is JS (R-M04), but the fetch completes in native code after the share activity has finished, possibly with no JS runtime. Start-up recovery (R-M02) would then mark a successful fetch `interrupted`. | Add state `fetched`: the body is held in app-private storage until JS extracts it, then deleted (R-M04 "raw HTML discarded" still holds). Recovery ignores `fetched`, and JS drains `fetched` items on every start. | **Applied 2026-10-02** (REA-14, ADR 0007) |
| F13 | R-M03 says "No other code path may initiate a network request", but R-M10 offers Retry. | Reword: a user-initiated Retry of a shared link is the same request. The R-M09 guard still allows only `Fetcher`. | **Applied 2026-10-02** (REA-14) |
| F14 | Failure actions disagree. R-M03 gives `fetch-failed` "Retry and Share the text instead" and the R-M10 table gives "Retry, Delete". R-M04 gives `extract-poor` "Share the text instead" and the table gives "Read anyway, Delete". | Use the union in both places: fetch-failed = Retry, Share-text guidance, Delete. extract-poor = Read anyway, Share-text guidance, Delete. | **Applied 2026-10-02** (REA-14) |
| F15 | The data model can't express two rules. (a) "Trim opens automatically the first time" needs an opened flag. (b) `archived` overwrites the prior state, so a restore can't tell `ready` from `extract-poor`. | Add `Item.openedAt?`. Make archive a separate `archivedAt?` field instead of a state. | **Applied 2026-10-02** (REA-14, ADR 0007) |
| F16 | The network guard only scans our sources. Bundled third-party JS (Readability, linkedom, RN) isn't covered, and the Kotlin rule "no file other than Fetcher opens a connection" would flag BridgeServer's inbound `ServerSocket`. | Add a runtime guard: in release builds, replace `fetch`, `XMLHttpRequest`, and `WebSocket` with throwing stubs before the app loads. Define the Kotlin rule as outbound (`Socket(`, `openConnection`, `OkHttpClient`), and allow `ServerSocket` only in `BridgeServer`. | **Applied 2026-10-02** (REA-14) |
| F17 | SPIKE-02 has no pass line ("acceptable speed"). | Proposed: a 5 MB page extracts in 10 s or less with no OOM, and an article under 1 MB in 1.5 s or less, on the reference device in a release build. | **Owner confirmed 2026-10-01** |
| F18 | The reference device has **two** TTS engines: `com.google.android.tts` is installed alongside `app.grapheneos.speechservices` (checked over adb 2026-10-01). The SRS lists one. Google's engine exposes network voices, which makes it the real test of R-M06's filter. | Correct the reference-device line. Use the Google engine for the R-M06 network-voice test. | **Applied 2026-10-02** (srs.md Background) |
| F19 | Unit tests run on Node (V8 with full ICU), but the app runs on Hermes. Segmentation and extraction can pass in Jest and still behave differently on the device. | Segment tests run both the `Intl.Segmenter` path and the forced-fallback path. Every TS pipeline module gets an on-device Hermes check (the Phase 0 probe harness). | Plan-level, no SRS change |
| F20 | Toolchain gap. Current RN (0.87.1, template 0.87.2) needs compileSdk 37, build-tools 37.0.0, NDK 27.1.12297006, Kotlin 2.2.0, and Gradle 9.4.1. This machine has only platform 34 and build-tools 34.0.0. | Phase 0 Task 1 installs them. | Plan-level |
| F21 | `GET /health` is unauthenticated and reports engine and voice, so any app on the device can see that Read Me's bridge is running and which voice it uses. | Accept as low risk (no item data). Record it in the bridge ADR. | **Accepted 2026-10-02** (REA-14; srs.md R-M12) |

## Owner decisions taken during planning (2026-10-01)

- F11: Kotlin owns the database (ADR 0001, written in Phase 0 Task 2).
- License policy: OSI only, except CC-BY-4.0 data-only packages listed by name (`caniuse-lite` today). ADR 0002, Phase 0 Task 2.
- Spike probe code stays on its `spike/rea-N-*` branch; only the recorded answer merges.
- F17: SPIKE-02 pass line confirmed as proposed (5 MB page in 10 s or less with no crash; every page under 1 MB in 1.5 s or less; reference device, release build).
- F12-F16 SRS amendments applied and F21 accepted (2026-10-02, REA-14).
- 2026-10-01: SPIKE-06's contention policy chosen by the owner: the bridge answers 503 while
  Read Me is playing (ADR 0004).

The Phase 0 plan was critiqued three times on 2026-10-01 (BLOCK 35, then CONCERNS 58, then CONCERNS 60); revision 4 resolves all findings. The latest verdict is in `.claude/last-critique.md`.
